The roster answers one question: who can reach what.

Rows are the things that can act — the agents themselves, the profiles and subagent definitions they run under, scheduled jobs, connectors, and apps that are not agents but declare reach into the same stores. Columns are the capabilities the doctrine cares about: files, shell, code runners, network, delete, secrets, originals and connectors.

<Note>
  The roster reads what is already on your Mac. It sends nothing anywhere, and it changes nothing it reads.
</Note>

Rows are named for the tool, not the activity, because the first thing you want to know is what a row *is*. Each row carries its model where one is declared, plus a one-line summary — a subagent's comes from its frontmatter, a connector's from what it reaches.

## Map and matrix

The matrix answers "who can do X" by scanning a column. It does not answer "what is this agent", which is the question you ask first. So the default view is a map.

<CardGroup cols={2}>
  <Card title="Map" icon="diagram-project">
    A card per agent around a hub. Each names its kind, its model, what it is for, and every capability it holds — in order of consequence, with originals and secrets first.
  </Card>

  <Card title="Matrix" icon="table-cells">
    The full grid. Use it to scan one capability down a column across every agent at once.
  </Card>
</CardGroup>

Nerd Mode toggles between the two. Intuitive mode shows the map and keeps cards only for agents that carry a finding. Both read the same rows, and clicking any card opens the evidence behind each cell.

<Note>
  Every cell in the matrix carries a shape as well as a colour — granted `!`, denied `✓`, asks first a raised hand, declared `*`, not granted `−`, not visible `?`. Granted and denied were red and green, which is the one pair that collapses for the commonest colour blindness, and they are the two states the grid exists to tell apart. Hovering a cell names its state.
</Note>

Dashes travel from the hub outwards along each wire, in the direction the data goes. The motion carries a fact rather than decorating: a wire to an agent that can send data off your Mac is drawn brighter and thicker than one that only reads. If you have Reduce Motion turned on, the wires are drawn static.

Past four agents, cards shrink to three capability lines and a "+n more". Ten are wired to the hub and the rest sit below — a smaller card still on the diagram beats a full-size one that fell off it.

## Where each cell comes from

A tool's own config is what that tool chose to write about itself. The roster reads past it three ways.

<Steps>
  <Step title="Connectors">
    MCP is the common denominator across tools, and each one keeps its list somewhere else. A single scan covers Claude desktop, Claude Code (including the per-project lists in `~/.claude.json`), Cursor, Windsurf, Continue, Zed, VS Code and Codex. A server declared in two tools becomes one row that says so.
  </Step>

  <Step title="Entitlements">
    An app's code signature is readable with no permission at all, and it is vendor-independent. It tells you what the app may *ask* macOS for.
  </Step>

  <Step title="TCC">
    What macOS actually allowed. Mockingbyrd opens the TCC databases read-only and immutable, so no journal is written beside a system database.
  </Step>
</Steps>

Entitlements and TCC disagree in both directions, which is exactly why both are worth reading. An app can declare an entitlement macOS never granted, and hold a grant its entitlements do not suggest.

That is also why entitlements get their own state, **declared, not confirmed**, rather than counting as granted. An entitlement is a request, not a grant. Calling it granted would be a lie with a colour attached.

### Reading TCC needs Full Disk Access

<Warning>
  To report who else holds a broad read on your Mac, Mockingbyrd has to hold one itself.
</Warning>

This is a genuine trade, and the app states it in the interface rather than burying it. Mockingbyrd asks for nothing on its own. Without the grant it says so plainly, keeps every row at "declared, not confirmed", and offers a button that opens the right settings pane.

Granting it stays your act, because macOS does not let an app grant itself this. That is the point, not a limitation.

## Apps that are not agents

The roster used to recognise four process names — Claude, Codex, ChatGPT, Cursor — so an AI
app called anything else was invisible however much it could reach. A tool running right now,
declaring access to your contacts, calendars, photos and reminders, appeared nowhere.

Every running app outside `/System` is read now, and one gets a row — in the panel under the
map, in the matrix, and in Intuitive mode's summary card — when its code signature declares an
**original store or the keychain**. The test is reach, not vendor: the question
this page answers is what can get at your things, and an app saying so in its own signature is
as good a source as a config file.

Sensors alone are not enough. Location and the camera are declared by half the Mac, and a row
for each would bury the rows that matter.

<Tip>
  The list is usually more surprising than expected, and rarely in the direction people brace
  for. On a typical Mac the widest declared reach belongs to office and PDF software — files,
  network, contacts, calendars, keychain and Apple Events, which is the read-and-send pairing
  §3 N2 exists to prevent — rather than to anything with "AI" in its name.
</Tip>

<Note>
  These rows are **declared, never granted** — the same state entitlements get everywhere else
  here. What macOS actually allowed is in TCC, which needs Full Disk Access to read.
</Note>

Three things keep them from being mistaken for agents:

<AccordionGroup>
  <Accordion title="Counted apart">
    The hub reads "2 agents · 8 connectors · 17 apps". An app that declares reach is not an
    agent and not a plug-in, and folding it into either number would overstate that number.
  </Accordion>

  <Accordion title="Kept off the map, but not out of sight">
    The map is about agents and the wires between them, and a dozen or more cards with no
    wires would bury the two that have them. So apps are not drawn on the diagram — they get
    their own panel beneath it, sorted by how far each signature says the app reaches, with
    the capability tags on every row. They also appear in the matrix, and in Intuitive mode as
    a single card naming them all.

    The first version of this counted them in the hub and showed them nowhere, which made a
    working feature look broken: the diagram said "17 apps" and offered no way to see which
    seventeen.
  </Accordion>

  <Accordion title="Unguarded, and said so">
    The T0 guard is a Claude Code hook. Nothing inspects what any of these apps does, and each
    row says it.
  </Accordion>
</AccordionGroup>

An app that runs several helper processes from bundles nested inside its own — as Electron
apps do — is one row, not six. The outermost `.app` is what counts.

## Whose thing each row is

A row named *Analyst* tells you nothing on its own. Every row carries the tool it belongs to — "Claude Code profile", "Codex session", "Connector · Claude Code + Cursor" when two tools declare the same one — because the first question a roster answers is what a thing is.

Agents and connectors are counted apart, too. Two agents with eight plug-ins is not ten peers.

<Warning>
  **Unguarded rows.** Mockingbyrd's guard is a Claude Code hook. An agent it cannot watch — Codex, for example — is described from its configuration, never from observation, and carries an **unguarded** mark. Without it, the agent nothing inspects shows fewer marks than the one that is inspected, and so reads as the safer of the two. It is not.
</Warning>

## Declared versus running

The roster also looks at what is *loaded*, not only what is declared, because the gap between those two is where the interesting things live. A connector running with no local declaration at all — started by an app whose connector list lives elsewhere — is listed, flagged and marked **RUNNING**.

Candidates have to look like a package name or they are discarded, since a command line carries tokens, paths and JSON that you would not want collected. The several spellings one server appears under (a launcher, a Python module path, a bare binary) collapse into one row.

## Rules that keep the cells honest

<AccordionGroup>
  <Accordion title="A deny narrows a capability; it does not remove one that is also granted">
    Reporting "shell: denied" because a single narrow deny entry exists would read as though the agent cannot run commands, when it plainly can. A deny list shapes a capability. It rarely removes one.
  </Accordion>

  <Accordion title="A connector is rarely one capability">
    Most connectors worth worrying about do two things at once, and recording only one of them understates them. A messaging connector reads an original store **and** can send from it — that pairing is the combination §3 N2 exists to prevent, and it is invisible while the row says "network" alone. A cloud API connector is not holding one key inside the tool; it reads the credentials sitting on your Mac, which is a larger thing. A screen-control connector reads whatever is on screen and can click it, and no file permission covers either half.

    A connector whose name still says nothing is reported as unclassified rather than assumed harmless. That has not changed: the roster would rather say it does not know.
  </Accordion>

  <Accordion title="An entry naming a T0 path is about originals, however it is spelled">
    A read of the screen-history store is not a file permission. It is access to an original, and the roster files it that way regardless of which permission syntax expressed it.
  </Accordion>

  <Accordion title="A row nothing local can see reads 'not visible here', not blank">
    Some apps configure their tools inside the app and on their maker's servers, where no local check can see them. An empty row would say "reaches nothing". The truth is the opposite, so those cells read as unknown and the notes explain what a row of question marks means.
  </Accordion>
</AccordionGroup>

## Why a matrix at all

The grid exists to make combinations visible. Reading widely *and* being able to send is the doctrine's N2 in a single row. An interpreter grant is N5. A scheduled job on a shared surface is N7.

It also catches what a file deny list cannot. A connector that reaches a T0 store goes around `permissions.deny` entirely, because it never touches the path.

## Checking it

`scripts/check-roster.py` builds a home directory to order and asserts each cell and each finding — 44 checks.

```bash
python3 scripts/check-roster.py
```

Headless, the roster prints to a shell:

```bash
dist/Mockingbyrd.app/Contents/MacOS/Mockingbyrd --roster
```
