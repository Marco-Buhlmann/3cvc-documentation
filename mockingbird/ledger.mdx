The ledger rebuilds token use and API-equivalent spend from session files that are already on your Mac.

<Warning>
  This is not a bill. It is what the same work would have cost at published API rates. If you are on a subscription, you were not charged these amounts.
</Warning>

## What it reads

| Source | What it records |
| --- | --- |
| `~/.claude/projects` | Claude Code writes usage per assistant turn |
| `~/.codex/sessions` | Codex writes `token_count` events per turn |

Codex records two figures per event. `last_token_usage` is that turn; `total_token_usage` is cumulative, so only one of them can be summed. `cached_input_tokens` is a subset of `input_tokens`, not an addition to it — counting both would inflate every total.

Nothing is written back to either directory, and nothing is sent anywhere.

## Prices

Cost comes from a built-in table of Anthropic rates, plus anything you add yourself in `prices.json`.

<Note>
  A model with no rate reports its tokens and a dash. It never reports a guessed figure.
</Note>

The per-file cache holds token counts only. Prices are applied when the cache is read, so editing `prices.json` re-prices your whole history immediately — there is no cache to clear.

### Keeping rates current

Published prices move, and a stale rate is worse than a missing one because it looks right. `--price-routine` writes a script that checks the public price lists and proposes an update:

```bash
dist/Mockingbyrd.app/Contents/MacOS/Mockingbyrd --price-routine
```

The fetch lives in that routine, never in the app: the app has exactly one request of its own, and it is not this one. The routine proposes; you apply. It records when it last ran, and the app shows you the age of your rates so you can tell fresh numbers from old ones.

## The charts

Cost and tokens by week sit between the totals and the tables, drawn in a single `Canvas` rather than through a charting library. That keeps the app dependency-free and gives full control over how a line reads on a dark background.

The tiles answer "the last 30 days" and the charts want your whole history, so the view builds the ledger twice. The second build is nearly free, because the per-file cache already holds it. Both modes draw the same chart.

## Headless

```bash
# Token use and API-equivalent spend, 90 days by default
dist/Mockingbyrd.app/Contents/MacOS/Mockingbyrd --ledger

# A different window
dist/Mockingbyrd.app/Contents/MacOS/Mockingbyrd --ledger --days 30
```

## Where the tokens went that did not need to

The ledger answers what your agents cost. The optimizer answers which of it was avoidable, from the same local transcripts.

```bash
Mockingbyrd --usage --days 30
```

Nine detectors, scored out of 100 and weighted the way the underlying research weights them — cache health 30, context hygiene 25, loops and fan-out 20, tools and connectors 15, reasoning 10. The score starts at 100, each area subtracts at most the points it is worth, and only an area's worst finding counts, so one problem is never charged twice.

The number is named as well as given: **85 and above** is efficient, **65–85** some waste, **40–65** wasteful, **under 40** very wasteful. The panel draws that scale and marks where you sit on it — a verdict with no boundaries behind it cannot be read, since 61 and 44 are both "wasteful" and one of them is nearly fine.

| | What it looks at |
|---|---|
| **Cache health** | The share of input served from cache, and the restarts and model switches that throw it away |
| **Context hygiene** | Sessions carrying context past 150K, the same file read twice, instruction files nobody trims |
| **Loops and fan-out** | Subagent runs and scheduled agents that spend while nobody is watching |
| **Tools and connectors** | Single results large enough to dominate a session, connectors declared but never called |
| **Reasoning** | Thinking as a share of output, billed at the output rate and never shown to you |

Four of the estimates are measured rather than modelled, and each finding records **which meter its tokens sat on** — fresh input, output, or cache read. Carried context is a cache read at a tenth of fresh input; pricing it as fresh input overstates the waste tenfold, which is a mistake this app made once on real data.

<Note>
  The optimizer reads whole sessions that **ended** in the window; the ledger counts turns by the day they ran. Both are right, they answer different questions, and each figure says which it used. They will not add up to each other.
</Note>

### Right-sizing, not recommending

It prices the traffic each model actually ran against the next model down, and says what the transcripts suggest about whether the work would survive the swap — a high thinking share is the worst candidate, heavy tool use the most plausible one. It never picks a model for you.

## Caps

The only part of the ledger that acts. Everything is off until you switch it on, and every limit is a number you set.

| Cap | What it does |
|---|---|
| **Read hold** | A file whose size implies more than the threshold pauses before it is read whole, so it can be paged or searched instead |
| **Session budget** | Stops to ask once a session has spent more than you allowed |
| **Daily budget** | The same across every session, today |
| **Unattended budget** | A tighter daily limit for work nobody started — decided by the process that launched the agent, not by whether the app is open |

Four presets — off, careful, everyday, lean — size themselves from this Mac's own busy days rather than its median ones, and each states **how often it would have stopped you** over your recorded history. That number, not the token count, is what tells you whether a cap is livable.

```bash
Mockingbyrd --preset everyday --dry-run   # what it would set, writing nothing
Mockingbyrd --preset off                  # clear every cap
```

<Warning>
  A cap that trips pauses the call and asks in Mockingbyrd. With the app closed there is nobody to ask, so the call stops. Anything that goes wrong *inside* the caps layer lets the call through — thrift never blocks work by accident, while the doctrine layers stay fail-closed.
</Warning>

## Checking it

`scripts/check-ledger.py` checks the arithmetic against hand-computed costs — 22 checks, covering cache invalidation, re-pricing from `prices.json`, and the cache-write premium.

```bash
python3 scripts/check-ledger.py
```
